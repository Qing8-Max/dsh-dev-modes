# 游戏开发交付流程

引擎无关的通用流程；Godot 的具体命令见第 7 节。其他引擎按同等原则使用它自己的运行器、测试与截图能力。

## 1. 核心玩法与验收标准

- 一句话说清核心循环：玩家反复做什么、反馈是什么、为什么好玩。
- 本次任务改变循环中的哪一环；验收标准是"可观察的行为"，不是"代码写对了"。
- 手感目标要可量化：移动速度、跳跃高度、冷却、命中反馈延迟。
- 明确不做什么（不做美术资源、不改存档格式、不动已发布的关卡）。

## 2. 现状调查

- 引擎与项目设置：分辨率、物理、输入映射、渲染管线、自动加载/单例。
- 相关场景结构与脚本：谁拥有这个机制、信号如何连接、状态放哪里。
- 资源管线：贴图/音频/模型如何导入，命名与目录约定。
- 已有测试与运行方式：怎么启动、怎么 headless 跑、怎么导出。
- 基线性能数据：帧时间、绘制调用、实例数、内存。

## 3. 最小可玩原型

- 先做能玩的最小闭环（占位图形、占位音效可接受），验证玩法成立再加内容。
- 原型与正式实现分开，别让原型代码渗进主场景。
- 每次只验证一个假设：好玩吗？可读吗？操作跟手吗？

## 4. 实现纪律

- 跟随项目的场景/节点/脚本惯例，不重排目录、不改公共接口除非任务要求。
- 玩法参数外露可调（导出变量/配置表），不要散落魔法数字。
- 一次只改一个维度，记录改前/改后数值与观察结果。
- 不改不删用户的场景、美术、音频、存档；确需改动先问。

## 5. 验证（必须真实运行）

- 用引擎自己的运行/headless 路径跑起来，读日志，确认没有报错。
- 视觉相关：截图或状态导出，和验收标准逐条对照；不要凭代码推断画面。
- 玩法相关：给出可复现的操作步骤与预期结果。
- 性能相关：改前改后各测一次，给出数字；没有数据不说"优化了"。
- 无法运行的验证，明确写出原因与未覆盖风险。

## 6. 交付

- 改动清单（场景/脚本/资源/配置）与每项作用。
- 验证记录：跑过的命令、日志要点、截图或数据。
- 手感/性能的前后对比；调参表。
- 未验证项、已知风险、后续建议。
- 用户没要求就不提交、不推送、不改发布/签名设置。

## 7. 引擎工作流（按项目加载）

先按项目文件识别引擎，再加载对应技能；本文件只留通用原则，引擎命令写在各自的技能里。

| 项目特征 | 加载技能 |
|---|---|
| `project.godot`、`*.tscn`、`*.gd` | game-godot |
| `ProjectSettings/ProjectVersion.txt`、`Assets/`、`*.unity`、`*.prefab` | game-unity |
| `*.uproject`、`Source/*.Target.cs`、`Content/` | game-unreal |
| `assets/` + `settings/` + `package.json`、`*.scene`/`*.prefab`（Creator） | game-cocos |
| 其它 / 自研引擎 | 按下面的通用适配清单自行落地 |

### 通用适配清单（任何引擎）

- 启动器与版本：可执行文件路径、项目版本文件；参数先用 `--version` / `--help` 确认，别照搬别的引擎命令。
- 无头运行与测试：命令、结果文件（XML/JSON）、退出码含义。
- 画面/状态验证：截图、状态导出、日志位置。
- 打包/导出：命令、预设或目标平台、产物路径；产物要真的启动一次。
- 沙箱与权限：引擎通常写用户目录的缓存/许可证；命令因权限失败时切到完全访问权限重跑，不要改引擎配置绕过。
- 资产约定：哪些是二进制（不要手改）、哪些是文本（可以 review）、哪些生成物不进版本库。

## 红旗清单（出现即停下确认）

- 需要删除或重建用户的场景、美术、音频、存档。
- 需要删除用户目录、系统目录或工作区以外的文件（即使是“清理”）。
- 需要改存档格式、导出/签名设置或发布流程。
- 无法真实运行却准备宣称"手感/性能变好了"。
- 玩法改动与既有设计意图冲突且用户未表态。
