# 软件开发交付流程

按顺序推进，每一步都留下可见的产出；信息不足时只问用户才能决定的事，其余自己查。

## 1. 需求澄清

- 目标：用户真正要解决的问题是什么（不是他提出的实现手段）。
- 范围：这次做什么、明确不做什么。
- 验收标准：怎样算完成，用什么命令或现象证明。
- 约束：技术栈、兼容性、性能、安全、发布时间。
- 若需求有歧义且无法从仓库推断，用一次提问集中确认，不反复打断。

## 2. 现状调查

- 读 `AGENTS.md` / `CLAUDE.md`、README、贡献指南里的约定。
- 找到构建、类型检查、lint、测试的命令（`package.json`、`Makefile`、`pyproject.toml`、`CMakeLists.txt` 等），先跑一遍基线。
- 找同类实现与既有模式：命名、目录结构、错误处理、日志、测试写法。
- 查依赖与版本约束；确认改动点的影响面（调用方、数据、配置、文档）。

## 3. 设计与计划

- 给出 1–2 个可行方案与取舍（复杂度、侵入面、可回滚性），选定一个并说明理由。
- 列出改动的文件清单、接口/数据结构变化、迁移与回滚方式。
- 非平凡改动先出计划、经用户确认再动手；计划写到可执行粒度。

## 4. 实现

- 保持最小正确改动：不顺手重构无关代码，不换依赖，不改公共 API 除非任务要求。
- 跟随仓库既有风格；新增依赖要给出理由。
- 分小步提交式推进，每步保持可构建、可测试。
- 同步补测试：改行为就改/加测试，修缺陷先写能复现的用例。

## 5. 验证

- 跑项目自己的命令，而不是自造的替代验证：构建 / 类型检查 / lint / 单元与集成测试。
- 失败先修再汇报；无法运行的检查，明确写出原因与未覆盖的风险。
- 需要手工验证的点，列成可复现步骤。
- 不要在验证缺失时用"应该可以工作"下结论。

## 6. 交付

- 改动清单：文件与作用，一行一个。
- 执行过的命令与结果（通过/失败/跳过）。
- 未验证项、已知风险、后续建议。
- 用户没要求就不提交、不推送、不改历史、不删数据、不动凭证。

## 红旗清单（出现即停下确认）

- 需要删除数据、重写历史、修改权限或密钥。
- 需要改动公共 API、数据格式或发布流程而无迁移方案。
- 测试无法运行却准备宣称完成。
- 需求与仓库现状冲突，且用户没有明确取舍。
